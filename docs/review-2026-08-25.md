## 〇、总评

先说优点，因为这决定了怎么读这份报告：**这是一个文档和"收口意识"远超平均水平的代码库**——
STATE.md 把 R2 key 布局、WS 帧协议、上传韧性语义写成了契约；每个文件头都有"为什么这么做"
的注释；2026-07-26 已经做过一轮 review 驱动的重构（commit `8a28524`：AgentSocket 基座合并
三路 WS、API.authed/get/send 收口、FeedRow 组合解码、tokenProvider 注入点），说明这个库
**有过且能执行重构纪律**。

但正因为如此，本次审查的核心矛盾很突出：

> **收口做了一半就停了，两套习惯长期并存。** Networking.swift 注释自称"~74 处样板的收口、
> 新调用一律走这里"，实际全仓 **72 处 `URLRequest(` 中只有 11 处走了 `API.get/send/authed`
> （约 13% 迁移率）**，其余 70 处手写样板散在 18 个文件里。同样的故事重复发生在：WS 生命周期
> （基座建好了，4 个客户端只有 3 个迁了）、正文行号契约（唯一真相源建好了，计数逻辑仍有 4~5 份）、
> 余额/邀请数据（接口就一个，5 处各自实现）。**这套代码不是没有架构，而是架构在"半迁移"状态里
> 僵住了**——这是最贵的维护负债形态：新代码和旧代码长得不一样，改任何公共契约要同时改两种写法。

## 一、重复代码（重点）

### 1.1 网络请求样板：70 处手写 vs 11 处 helper

`Networking.swift:165-198` 提供了 `API.authed/get/send`，但：

- 全仓 `URLRequest(` 共 72 处，70 处在 Networking.swift 之外手写，分布于 18 个文件；
- 大户：**Library.swift 16 处**、**Community.swift 13 处**、SettingsView.swift 10 处、
  PromptStore.swift 8 处、BooksShelfView.swift 4 处、PhotoService.swift 3 处、DeviceLink.swift 3 处；
- **同一个文件内部都混用两种风格**：SettingsStore 里 10 处手写样板（`:77/105/124/142/158/178/235/251/272/325`）
  旁边就躺着 3 处 `API.get/send`（`:97/213/225`）；且样板互相不一致——`load()` 用
  `httpStatusCode`+手动 200..<300（`:81-82`），`loadStyleHistory()` 用 `resp.isOK`（`:108`），
  同一语义三种写法；
- 最典型的两对"同一请求的两个副本"：`Library.swift:865-878` `restyle()` 与 `:909-931` `remine()`
  （都是 POST `/agent/restyle`，仅 payload 差一个字段）；`fetchDoc`（`:676-689`）与 `fetchDocRaw`
  （`:699-709`）是同一个 GET 的解码/不解码两版；
- 连带问题：**登录门槛样板 11 处**（`guard !token.isEmpty else { error = "请先登录"…}`，
  Library×3 / PromptStore×4 / SettingsView×4）、`"application/json"` 字面量 30 处、
  `setBearer` 68 处、`JSONDecoder()` 50 处——全部是"改 bearer 头/超时/编码要改 70 个地方"的坑。

### 1.2 正文行号 / 分段契约：同一语义 4~5 份独立实现（最高危的重复）

"按非空 trimmed 行切分 + photo 标记占号"这条正文契约，在 App 里被独立实现了 **4 份**
（加 Library.swift 内第 5 份）：

| 实现 | 位置 |
|---|---|
| `bodyRows`（详情页行号渲染） | `RecordingDetailView.swift:865-866` |
| `BodyDiff.rows`（追问 diff） | `FollowupQuestions.swift:122` |
| `MarkdownTextBlock.lines` | `MarkdownBlock.swift:149-153` |
| 段落化（导出） | `ExportManager.swift:271-273` |
| `replacingLine`（第N行替换） | `Library.swift:145-180` |

**"第N行连续计数（photo 占号）"3 份**，全靠注释对齐、无共享函数：
`RecordingDetailView.swift:860-876`、`Library.swift:145-180`（注释写着 "matching bodyRows's
第N行 counter"——单向注释耦合，bodyRows 改规则时 replacingLine 不报错，只在行号漂移时出 bug）、
`FollowupQuestions.swift:120-129`。行号还通过 `{{LINE}}` 占位符**拼进发给 agent 的指令文本**
（`RecordingDetailView.swift:945` → `PromptStore.swift:365+`）——改行号规则 = 改 3 处计数代码
+ 服务端 prompt 契约。

行内 markdown 解析也两份：`MarkdownBlock.swift:72-76` vs `RecordingDetailView.swift:1058-1065`
`textAttributed`（同一套 `AttributedString(markdown:options:)` 重写，只多了个缓存；缓存本应放
MarkdownBlock 里）。

### 1.3 WS 生命周期：1 个基座 + 4 套实现、重连策略 2 套、帧解析 5 份裸字典

`AgentSocket.swift`（174 行）已把心跳 25s / 重连 1.5s / generation 代际收口，注释称合并了三路
WS——**但只迁了 Article/LibraryCommand/Status 三个**：

- **4 个 WS 生命周期实现并存**：AgentSocket（收口版）＋ `RealtimeSession.swift:31-90`（内联手写
  closed/generation/receive，无心跳）＋ `DeviceLink.swift:183-270`（又一套，无心跳无代际）＋
  `VoiceEdit.swift:217-235`（SpeechDictation 自己开 socket）；
- **重连策略两套语义**：AgentSocket 固定 1.5s 无限重连（`:153-161`，对 token 失效场景会无脑撞
  服务端）vs `RealtimeInterviewer.swift:107-122` 指数退避 1/2/4…32s ×6 次；
- **WS 帧解析 5 处全部是 `JSONSerialization → [String:Any] → obj["type"] as? String → switch`
  裸字典**，零共享零类型：AgentSession `:216-218`、LibraryCommandSession `:138-140`、
  StatusSession `:32-34`、RealtimeSession `:93-94`、DeviceLink `:273-275`。讽刺的是 HTTP 响应侧
  反而全是 struct+JSONDecoder——**最不稳定、最该有类型保护的 WS 帧全裸奔**；
- **ArticleAgentSession vs LibraryCommandSession 约 85% 逐行同构**（connect/enqueue/resubmitAll/
  handle 四分支/reconcile/persist/disconnect 逐字相同），无共享状态机；且 LibraryCommandSession
  的 `queue` 直接复用 `ArticleAgentSession.EditRequest` 类型（`LibraryCommandSession.swift:31/56/84`），
  "库级命令"与"文章编辑"两个概念被绑死在一个 struct 上，`VoiceAgentSession` 协议（16 行）形同虚设。

## 二、架构问题

### 2.1 God file × 5（可维护性的头号障碍）

| 文件 | 行数 | 症状 |
|---|---|---|
| `RecordingDetailView.swift` | 1553 | **39 个 @State**、直持 6 个状态对象（LibraryStore/CommunityStore/SettingsStore/ArticleAgentSession/SpeechDictation/FollowupState）、15+ 职责（播放/doc/版本/风格/微信/社区/小红书/语音编辑/追问/插图/长按/键盘精修/提示/分享/删除）、内嵌 6 个独立类型、两套播放 UI 并存 |
| `Community.swift` | 1243 | store + 模型 + 缓存 + 分享 UI + 录音回应链路 + 举报/屏蔽全塞一个文件 |
| `SettingsView.swift` | 1221 | **16 个顶层声明**，SettingsStore 一人扛文风+名字+微信+CONFIG+邀请+反馈+余额 7 个域，`load()` 里 5 个网络请求串行 await |
| `PromptManagerView.swift` | 1218 | 单 struct，视图粒度过粗 |
| `Library.swift` | 1120 | store god object：约 25 个手写 API 方法 |

### 2.2 全局状态碎片化：10+ 单例、6 个 store、双实例分叉

10 个 `static let shared` 单例（AuthStore/Uploader/BackgroundTransfer/PhotoUploadQueue/PromptStore/
ReferralManager/StoreService/Prefs/WeChatShare/AppRouter）+ LibraryStore/CommunityStore/
BooksShelfStore/SettingsStore/DeviceLinkStore 等。最危险的例子：**CommunityStore 有两个实例**
（`LibraryView.swift:13` 和 `RecordingDetailView.swift:32` 各自 new），跨实例同步靠 DiskCache 文件
+ UserDefaults 字符串 key（`Community.swift:1024 ↔ LibraryView.swift:369-377`）握手——这直接导致
下面的 unshare/report bug。

### 2.3 两套「钱」无统一模型

订阅（StoreService/StoreKit2）与算力余额（服务端 usage ledger）是两套独立状态：余额 3 个界面各自拉、
**没有"钱变了"的广播**——ReferralManager 到账只弹 toast（`RootView.swift:15-23`），购买成功后只有
UsageView 自己重拉，设置页算力行与写书页**保持陈旧数字**。StoreService 混用 `ObservableObject`
老范式、`claim` 失败静默（`:110-111`）。

### 2.4 三种进度通路并存

挖矿 = WS 推送（StatusHub）；修书 = 6s HTTP 轮询（`BookReviseSheet.swift:213-218`）；写书 =
**零反馈**（fire-and-forget，最贵的 320 算力功能反而唯一没有进度通道）。

### 2.5 乐观更新三套实现、回滚不对称

`commitEdit`（RecordingDetailView.swift:977-989）失败只 toast **不回滚本地 doc**；`toggleCommunity`
（`:733-756`）失败会恢复原布尔；undo/redo 的 `patchHead` fire-and-forget 失败无提示。无统一
"乐观更新→服务器→冲突解决"抽象。

### 2.6 测试覆盖严重失衡（维护安全网缺口）

191 条测试里 **PromptStore(73)+PromptDrag(24) 占 51%**；而最该有测试的**零覆盖**：LibraryStore
（文章生命线）、CommunityStore、Uploader、AuthStore、StoreService、**5 个 WS 帧解析器**、
**整个 Share Extension（9 文件，TEST_HOST 挂不到 extension target）**、relay 发布主链
（digest/cover/40007 重试链）。历史事故（jetsam OOM、照片-音频竞态、静默丢分享）恰好都出在零覆盖区。

## 三、维护性大坑（含 5 个真实 bug，按影响排序）

**① 数据丢失窗口（高）**：`RecordSession.swift:283` `promote` 先 `await location.placeTag()` **后移动
文件**；onDisappear/中断路径是 fire-and-forget `Task`。stop 之后、placeTag 返回之前进程被杀 → 文件
留在 staging 名 `recording-<ts>.m4a`，而 `AudioRecorder.cleanupStaleStaging`（`:164-171`）启动时
**无条件删除所有 staging 文件** → 这条录音永久丢失。文件移动应发生在任何 await 之前。

**② 编辑 socket 永久断线（中，真实 bug）**：`RecordingDetailView.swift:51` `connected` 标志只置
true 永不复位（`:345-346`）。详情页上盖任何 sheet（换风格/照片/微信设置）触发 onDisappear（`:255`）
断开 socket，sheet 关闭后 `.task` 重跑 `connectIfNeeded` 被 `guard !connected` 挡住 → **编辑功能
静默失效直到退出重进**。

**③ 库级命令重启恢复丢 refs（中，数据 bug）**：`LibraryCommandSession.persist()`（`:129-133`）存了
`refsJSON`，`connect()` 恢复时只取 `id + text`（`:56`）——杀进程后重发的库级命令丢了当时的 refs 列表
（对比 AgentSession 恢复时正确带回 anchor/itemId）。

**④ 取消分享/举报乐观更新不一致（中）**：`Community.swift:301/442` unshare/report 只删 `posts` 不动
`timeOrdered`（"最新" tab 数据源），也不 `persistFeedCache()`——最新 tab 仍显示、冷启动缓存重放已删帖。
根因就是 2.2 的双 CommunityStore 实例。

**⑤ 删号后推送静默断（中）**：`PushRegistrar.upload` 只在启动注册回调里跑一次（`:24-28`）。删号→
`resetAnonymous` 换新身份后，新 scope 的 `push-token.json` 没人写，**新身份收不到「文章已生成」推送
直到下次冷启动**。

**⑥ 其余大坑**：

- 魔法字符串：商品 ID 内嵌价格 `monthly_19_9`（StoreService.swift:15，改价=改 ID=老订阅失效）、
  微信白名单 IP `66.42.45.128` 硬编码进 App UI（SettingsView.swift:1057，VPS 换 IP 就要发版）、
  **第 4 个 host `lab.jianshuo.dev` 不进 API 枚举**（BookWritingSheet.swift:38、
  BookReviseSheet.swift:27-28）、`"pref.highQuality"` 三处直读、WS 路径拼接四种风格；
- 隐式契约：行号规则三处注释约定、photo key 拼接受型化缺失——`coverPhotoKey`（已拼好的完整 key，
  **不能再 join**）与 `photos[]`（相对 key，**必须 join**）两种语义相反的形态共存于 wire，类型都是
  String，三处拼接（Community.swift:737/1086/1217）零归一化，极易双重前缀；
- NotificationCenter selector 观察者无 `removeObserver`（AudioRecorder.swift:47-54、
  EngineRecorder.swift:81-93）——悬垂指针崩溃源；
- 死代码清单：`CommunityStore.isShared`（同一端点的第二个实现）、`refsJSON` 只写不读、
  `VoiceEdit.swift:129` `sequence` 死字段 + `:279-281` `sendAudio` 死方法、AgentSession 的 preview
  帧解析（唯一调用方 RecordingDetailView.swift:375 明说 UI 已撤）、`DeviceLinkCrypto.selfTest`、
  `AgentImage.base64`、`SettingsStore.wechatThumbMediaId` 空转往返、「经典录音引擎」逃生门
  （注释自认"稳定后删除"，双后端长期共存）；
- 误导注释：`PhotoUploadQueue.swift:124` "后台保活（同 Uploader）"——Uploader 并无此机制（音频=系统
  后台会话，照片=前台 ~30s assertion，韧性架构不同却宣称同构）；`VoiceEdit.swift` 注释说
  "log unhandled types"实际 `break` 没 log；`EngineRecorder.swift:9` "same contract as
  Prefs.recorderSettings"实为重抄。

## 五、最该先动的 8 件事（按收益/成本排序，跨模块合并）

1. **完成 API 样板迁移（70→0）**：Library.swift(16) → Community.swift(13) → SettingsView.swift(10)
   → PromptStore.swift(8)。样板已建好只用了 13%，机械迁移、风险低、每处都是未来的坑。顺带消灭
   同文件内 isOK/httpStatusCode 混用。
2. **拆 RecordingDetailView + 收敛正文契约**：把 39 个 @State 按职责拆成子 View/ViewModel；在
   ArticleBody 上加 `numberedRows(_:)` 让 bodyRows/BodyDiff/replacingLine 共用，删掉 3 处行号计数
   和 5 份分段实现——同时修掉"改行号规则要改 3 处代码 + 服务端 prompt"的契约漂移。
3. **合并 WS 会话 + 建帧解析层**：把 Article/Library 的共享模板抽成 `AgentVoiceSession<Payload>`
   基类（顺带修 refs 恢复 bug），帧名/状态值收敛成 enum + 一个 `AgentFrame` 解码器 + 客户端单测——
   服务端协议变更第一次有编译+测试兜底。
4. **建 `SuanliStore` 收口余额/邀请**：5 处 fetch / 5 份 decodable → 1 个 store；订阅 claim 成功、
   ReferralManager 到账、换身份时统一广播刷新——修掉"购买后余额陈旧"的功能 bug。
5. **修 5 个具体 bug**（都是小改动、大影响）：① promote 文件移动提到任何 await 之前；② `connected`
   在 onDisappear 复位；③ unshare/report 补删 timeOrdered + persistFeedCache（并把 CommunityStore
   单例化，根治双实例）；④ 删号/换身份后补传 push-token；⑤ NotificationCenter 加 removeObserver。
6. **收编共享小工具**：把 Color(hex:)/Theme token、clockString/formatDuration、SquareImage
   （参数化消灭 640/1080 漂移）、AudioPlayer 收进双 target 共享文件（沿用 Networking.swift 模式，
   一次 project.yml sources 改动）。
7. **补测试**：Share Extension 纯逻辑（ShareRouter.classify、SquareCrop.jpeg、decodeEntities/
   Readability——全是纯函数可测）、relay 的 digest/cover/40007 重试链、5 个 WS 帧解析器。
8. **relay 结构化异常**：`_wechat_err` 的正则解析改成直接抛 `WechatError{errcode, errmsg}`。

**一句话总结**：这个库的架构底子不差、文档是模范，但卡在"收口半途而废"——70:11 的请求样板比例、
4~5 份正文行号契约、4 套 WS 生命周期、5 处余额实现，都是同一模式：**真源建好了，旧拷贝没删干净**。
最紧迫的不是新增能力，而是把上面 8 件事里第 1~5 件做完，把两套习惯收敛回一套——否则每加一个功能，
都会在两种写法里各复制一遍，漂移只会越滚越大。
